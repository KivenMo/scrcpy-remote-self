# 远程协助（iPhone 控制安卓手机）

用一台 **iPhone** 看到并操作一台 **安卓手机** 的屏幕：点击、滑动、返回/主页/多任务、往输入框打字、打开指定 App。

- 被控端是安卓 App，**不需要 root**
- 控制端**不需要装 iOS App** —— iPhone 用 Safari 打开一个网页就能当遥控器
  （所以不需要 Mac、不需要 99 美元开发者账号、不用过 App Store 审核）
- 两端都是**主动外连**到中继服务器，所以不需要公网 IP，也不用打 NAT 穿透

> 反过来（安卓控制 iPhone）**做不到**。iOS 不允许任何第三方 App 被远程控制，这是 Apple 的平台限制，所有厂商都绕不过去。

## 二、架构

```
iPhone（Safari 网页）  ──WebSocket:8080──▶  中继服务器  ──原始 TCP:8081──▶  安卓被控端 App
        ▲                                        │                              │
        └────────── 画面（H.264 / JPEG）─────────┘◀────────── 画面 ──────────────┘
                       触摸指令 ─────────────────▶              ──────▶ 无障碍服务注入
```

服务器只做「配对 + 转发」，**不解码画面、不落盘**。

### 两种编码方式，控制端可随时切换

| | H.264（默认） | JPEG |
|---|---|---|
| 安卓端 | `MediaProjection` → Surface → `MediaCodec` 硬编 | `MediaProjection` → ImageReader → 逐帧压 JPEG |
| 控制端 | WebCodecs `VideoDecoder` 硬解 | `createImageBitmap` |
| 720p 带宽 | 约 **1.5 Mbps** | 约 3~5 Mbps |
| 兼容性 | 需要 Safari 16.4+ / Chrome 94+ | 任何浏览器 |

控制端连上后自动协商：支持 WebCodecs 就请求 H.264，被控端回一份
`avcC` 配置（`vcfg`）；3 秒内解不出画面、或浏览器不支持，就自动退回 JPEG。
也可以在「画质」面板里手动锁成 JPEG。

### 上行二进制帧格式（服务器透明转发，只由两端解析）

```
[0]      kind   0x01 = 整帧 JPEG
                0x02 = H.264 分片
                0x03 = 文件分片（被控端 -> 控制端）
[1]      flags  bit0 = 关键帧（I 帧，仅 H.264 有意义）
[2..9]   pts    无符号 64 位大端，微秒（文件分片用不到，填 0）
[10..]   payload
```

三种帧共用一条通道，服务器一视同仁地透传。控制端在 `parseFrame()` 之后按 `kind` 分流：
`0x01` 画、`0x02` 送解码器、`0x03` 攒成文件。
（文件分片**不计入**右上角的画面带宽统计，不然传文件时那个数字会没法看。）

H.264 分片用 **AVCC 长度前缀**而不是 Annex-B 起始码——因为 WebCodecs 在给了
`description`(avcC) 时要求这种格式。安卓端 `MediaCodec` 吐出来的是 Annex-B，
所以在 `CaptureService.annexBToAvcc()` 里做了转换。

### 安卓 ↔ 服务器的 TCP 分帧

```
[4 字节大端长度][1 字节类型][负载]     0x01 = JSON 指令   0x02 = 二进制画面
```

### 剪贴板互通

控制端网页里点「剪贴板」：

- **发送到手机** —— 走 `clip` 指令，被控端写进系统剪贴板；勾上「并粘贴」会额外
  往当前焦点输入框触发一次 `ACTION_PASTE`，省得你在手机上再长按一次。
- **从手机取回** —— 走 `clipget` 指令，被控端回一条
  `{t:'clip', src, v}`，其中 `src` 有三种取值：

  | `src` | 含义 |
  |---|---|
  | `clipboard` | 正常读到了系统剪贴板 |
  | `focused` | 剪贴板读不到，退回读了**当前焦点输入框**里的文字 |
  | `none` | 两者都没拿到，`v` 为空 |

> Android 10 起，**读取**剪贴板只允许正在前台的应用做。被控端是后台服务，
> 所以 `focused` 这条退路是常态而不是异常。写入没有这个限制。

### 文件传输（控制端 → 被控端）

服务器早就有一条长连接，所以没有新增协议，只是多复用了一个「二进制下行」通道：

1. 控制端发 `{t:'fstart', name, size, mime}`
2. 紧接着把文件切成 **64KB** 一片，以 WebSocket 二进制帧发出去
   （服务器只做字节透传，不解析）
3. 发完发 `{t:'fend'}`，被控端落盘

被控端在 Android 10+ 上通过 `MediaStore.Downloads` + `IS_PENDING` 写入
**系统「下载」目录**，不需要任何存储权限；更老的系统退到 App 私有目录。

背压：控制端盯着 `ws.bufferedAmount`，超过 4MB 就暂停读文件，避免把内存撑爆。
文件名会被清洗（去掉 `/ \ :` 和控制字符，截断到 120 字符），防止路径穿越。

### 从手机取文件（被控端 → 控制端）

反方向复用**同一条**二进制通道和**同一套 10 字节帧头**，只是 `kind` 换成 `0x03`，
所以中继服务器一行都不用改，控制端也只在 `parseFrame()` 之后按 `kind` 分流。

1. 控制端点「取文件」→ 发 `{t:'flist'}`
2. 被控端查媒体库，回 `{t:'flist', items:[{id, name, size, kind, mime, date}]}`
3. 控制端点某一条 → 发 `{t:'fget', id}`
4. 被控端回 `{t:'fbegin', name, size, mime}`，然后按 64KB 分片推 `kind=0x03` 的帧，
   最后 `{t:'fdone', ok}`。控制端把分片拼成 Blob，触发浏览器下载。

**只列媒体库（照片 / 视频），不列任意目录** —— Android 10 起是分区存储，
第三方应用没有权限随便读别人的文件。能干净拿到、且只需要一个常规运行时权限的
就是媒体库，所以只做媒体库。权限在被控端 App 里有一个独立的「授权」按钮，
**不授权只是这个功能不可用，其余一切照常**。

| Android 版本 | 需要的权限 |
|---|---|
| 13+ | `READ_MEDIA_IMAGES` / `READ_MEDIA_VIDEO` |
| 8~12 | `READ_EXTERNAL_STORAGE`（清单里标了 `maxSdkVersion=32`） |

被控端**边读边发**，分片之间睡 2ms 让路给画面；`sendPacket` 本身是阻塞写，
socket 缓冲满了自然降速，不需要额外做流控。控制端拿到 `fbegin.size` 为 0 时
（个别设备媒体库不报大小）会放宽校验，只按实际收到的字节数算。

### 震动反馈（默认关闭）

点被控手机的时候给一下触感，手感会好不少。但这件事在 iOS 上很别扭：

- **`navigator.vibrate()` 在 iOS Safari 上是静默失效的**，不是权限问题，就是不支持。
- 唯一能出触感的办法，是让用户**真实点到** `<input type="checkbox" switch>`
  （Safari 17.4+ 的系统开关控件）。所以要在画布上盖一层透明 `<label for="...">`，
  由 label 把点击转发给隐藏的开关，系统才给一下触感。
- 这一层毕竟改变了触摸落点，而且依赖未公开行为，所以**默认关闭**，在「画质」面板里开。
  关掉就是完全恢复原状。

为了让开关震动永远不会影响正常的触摸，代码做了两件事：

1. 触摸统一绑在 `#surface` 这一层容器上，`#hapticLayer` 只是它的一个可选子元素 ——
   开关震动不改变任何事件绑定。
2. `touchstart` / `touchend` **故意不调用 `preventDefault()`**。一旦调了，浏览器就会
   取消这次手势的默认行为，label→switch 的点击转发也就没了，iOS 上永远出不来触感。
   页面不滚动、不缩放靠的是 CSS 的 `touch-action:none`，不靠 preventDefault。

Android 浏览器走标准的 `navigator.vibrate()`，没有这些问题。

### 自动重连

两端都会自己重连，都用指数退避：

| 端 | 触发 | 退避 |
|---|---|---|
| 控制端网页 | `ws.onclose` 且用户没主动断开 | 800ms 起，每次 ×2，封顶 10s |
| 安卓 App | TCP 断开 | 1s 起，每次 ×2，封顶 15s |

重连成功后控制端会重新发 `hello` 入房，被控端画面继续推，**用户不需要任何操作**。
这一条被 `test-features.js` 用「真的把中继进程杀掉再拉起来」的方式验证过。

> **一个容易忽略的坑：`onopen` 会把退避计数清零。**
> 如果服务器接受了 WebSocket 握手、但随后就把连接关掉（限流、配对码被拒等），
> 那么每次重连都会走到 `onopen` → `reconnectAttempt = 0` → 退避永远涨不上去，
> 变成固定 800ms 一次的硬撞。所以被限流时不能只靠退避，
> 服务端会在 `error` 里带 `retryAfterMs`，控制端据此把重连推迟到解封之后（见 11.9）。
> 靠「连不上」来触发退避的场景（比如中继真的挂了）不受影响，因为那时 `onopen` 不会执行。

### 码率自适应

被控端记录每一帧的**实际写入耗时**，和帧间隔比：

- 连续 2 帧写入耗时 > 帧间隔的 85% → 判定拥塞，码率 ×0.75
- 连续 8 帧写入耗时 < 帧间隔的 35% → 判定富裕，码率 ×1.15
- 降有 400ms 冷却、升有 1200ms 冷却 —— **降得比升得快**，避免抖动

H.264 直接改 `MediaCodec` 的 `PARAMETER_KEY_VIDEO_BITRATE`（不重建流水线，
所以不会闪屏）；JPEG 则把码率映射成 JPEG 质量（25~95）。

这段逻辑在 `RateController.java` 里，**纯 Java、不依赖任何 Android 类**，
所以能直接用 `javac` 跑单测（24 项），不用开模拟器。

当前档位会通过 `{t:'net', kbps, level, codec}` 每 2 秒报给控制端，
显示在右上角的徽标里（`良好` / `一般` / `较差`）。

## 三、快速开始

### 1. 启动服务器

在一台电脑上（和被控手机同一个 WiFi，或者有公网地址）：

```bash
cd remote-assist/server
node server.js
```

输出会列出可用的局域网地址，例如：

```
[09:12:01] 被控端接入端口  TCP  0.0.0.0:8081
[09:12:01] 控制端访问地址  HTTP 0.0.0.0:8080
[09:12:01]   局域网可用： http://192.168.1.10:8080
```

需要 Node.js 18 以上。**不需要 npm install**，零依赖。

改端口：`HTTP_PORT=9000 TCP_PORT=9001 node server.js`

### 1.1 跑测试（可选，但建议）

```bash
# 只有 test-h264-e2e.js 需要先在另一个终端里 node server.js；
# 其余几个都自带中继（各自用 18xxx 端口，不会跟你 8080 上的那个打架）

# 中继：配对、双向转发、多控制端广播、错误配对码、掉线通知、mode 透传 —— 23 项
node test-relay.js
```

## 五、能力边界（重要）

免 root 能做和不能做的，都是 Android 平台本身定的，不是代码偷懒：

**能做到**

- 实时看到手机画面
- 点击、滑动、返回、主页、多任务、下拉通知栏
- 打开指定的 App
- 往输入框写文字、触发回车
- 剪贴板双向同步（发验证码、链接很方便）
- 往手机传文件（落在「下载」目录）
- 把手机上的照片 / 视频取回本机
- 点按时给一下震动（iOS 需要 Safari 17.4+，且默认关闭）

**做不到 / 需要 root**

| 限制 | 原因 |
|---|---|
| 锁屏界面输入解锁密码 | Android 禁止无障碍服务在安全锁屏上输入 |
| 银行 / 支付 / 密码框：看不到也点不了 | 这类界面带 `FLAG_SECURE`，录屏 API 直接返回黑屏 |
| 不弹授权就静默开始投屏 | `MediaProjection` 的授权弹窗是强制的，Android 14 起**每次开始投屏都要重新授权**，无法复用 |
| 重启后自动恢复控制 | 重启后必须有人手动解锁手机并重新授权 |
| 后台应用偷偷读剪贴板 | Android 10 起只有前台应用能读；取不到时本程序退回读焦点输入框 |
| 从手机取任意文件（比如微信聊天里的文件） | Android 10 起分区存储，第三方应用读不到别人的私有目录；只能读媒体库里的照片和视频 |
| iOS 上稳定地出震动 | 没有公开 API，靠系统开关控件的未公开行为，见第二节 |

**结论：这是一个「有人在场」的协助工具**（帮爸妈操作手机、远程指导），
不是「偷偷监控」的工具。这一点上，商业软件（RustDesk / AirDroid / TeamViewer）也完全一样。

**代码层面的已知取舍**

- 上行和下行共用一条 TCP 连接。网络很差时，画面写入阻塞会顺带拖慢点击指令的响应。
  局域网下感知不到；要彻底解决得把画面单独走一条连接或换成 WebRTC。
- H.264 走的是 `MediaCodec` 硬编，个别老旧机型对 `Surface` 输入的 baseline profile
  支持不好，代码里会自动去掉 profile 重试，再不行可以手动切 JPEG。
- **画面静止时编码器根本不产帧**（`MediaProjection` 只在屏幕有变化时才吐新帧）。
  在真机上实测过：手机停在同一个界面不动，10 秒里一帧都没有；
  主动 `setParameters(REQUEST_SYNC_FRAME)` 也没用 —— 编码器没有新的输入，
  要关键帧也要不出来。所以「靠每 2 秒要一个关键帧」这个想法是**错的**，
  已改成**被控端缓存最近一个关键帧，新控制端一连上就补发**（见第九节第 3 条）。
  不缓存的话，「手机放公司、你从家里连上去」会看到一片空白，直到公司那台屏幕上有什么动了为止。
- 手机横竖屏切换会重建编码器，切换瞬间画面会闪一下，属正常。
- 传文件没有断点续传：传到一半断网，被控端会把半截文件删掉，需要重传。
- 传文件时画面和文件抢同一条 TCP 连接。传大文件会明显压低画面帧率，
  这是「先能用」的取舍；真要解决得给文件单开一条连接。
- 被控端收到文件后**不弹任何通知**（`MediaStore` 只在系统「下载」里出现一条记录）。
  如果你需要「传完了告诉我」，得再补一条回执。
- 取文件（被控端 → 控制端）只能取**媒体库里的照片和视频**，取不了任意路径。
  想取别的类型得申请 `MANAGE_EXTERNAL_STORAGE`（特殊权限，上架会被重点审）。
- 取文件时整个文件是先攒在控制端内存里再拼成 Blob 的。取几百 MB 的视频会吃内存，
  真要取大文件应该改成流式写盘（`showSaveFilePicker` 或 `FileSystemWritableFileStream`）。

## 六、常见问题

**连不上服务器**
- 检查电脑防火墙是否放行了 8080 和 8081 两个端口
- 被控手机和服务器要在同一网段；跨网段需要服务器有公网 IP 或做端口映射
- 浏览器里打开 `http://服务器IP:8080/health` 能看到 JSON，就说明服务端是好的

**能看画面但点不动**
- 无障碍服务没开，或被系统杀掉了。回 App 首页看「无障碍服务」那行是不是绿色
- 部分厂商需要额外允许「后台弹出界面」

**画面是黑的**
- 当前界面是 `FLAG_SECURE`（银行、支付、密码框），正常现象
- 或者是锁屏界面，解锁后再看

**画面卡顿 / 延迟高**
- 切到「流畅」档
- 优先走 5GHz WiFi，别用 4G/5G 流量
- 把服务器放在离两端都近的网络里

**打不开 App**
- 极少数应用禁止被无障碍启动，会回一条「打开失败」提示

**手机重启后**
- 需要重新打开 App、重新授权录屏（系统限制，无解）

## 七、安全与合规

这个项目**故意做得很简单**，请在明确的前提下使用：

- **只能在你自己拥有的设备，或对方明确知情并同意的设备上使用。** 未经同意操作他人手机在大多数地区是违法的。
- 配对码就是唯一凭据，8 位（约 2.8 万亿种组合），**不要泄露**。想换就点 App 里的「换一个」。
- 当前默认是 **明文传输**（HTTP / 裸 TCP），适合局域网。放到公网前**必须**加密：
  ```bash
  bash tools/make-cert.sh          # 生成证书 + 指纹
  TLS_CERT=server/certs/cert.pem TLS_KEY=server/certs/key.pem node server/server.js
  ```
  然后 App 里勾「加密连接（TLS）」。完整说明见**第十一节**（含自签 / Let's Encrypt 的区别、
  反代怎么挂、以及怎么验证加密真的在生效）。
  也可以走反代（Nginx / Caddy 做 HTTPS + WSS），或套 WireGuard / frp + TLS 隧道。
- **TLS 只保证传输不被偷看篡改，不解决「配对码被磨」。** 中继现在自带猜码限流
  （5 分钟内试满 6 个**不同**的错码就封 IP 10 分钟，同一个码反复重试不受影响），
  但 `/health` 默认会把在线配对码公开出去，公网部署**必须**设 `HEALTH_TOKEN`，
  并给被控端端口做 IP 白名单。详见 **11.9**（含「挡不住什么」）。
- 服务器不保存任何画面，进程退出即清空。

## 九、真机上踩出来的 bug（含两个让 H.264 彻底不工作的）

前两条是写测试逼出来的，后三条是**插上真机（华为 P30 Pro / Android 10）跑的时候才暴露**的。
后面这三条尤其值得看 —— 它们的共同点是「本地测试全绿，真机上静默失败」：

**3. avcC 少算了 1 个字节 → 华为手机上永远没画面。**

真机日志：

```
I CaptureService: H.264 管线 720x1552 @12fps 1500kbps
W CaptureService: 解析编码参数失败: java.lang.ArrayIndexOutOfBoundsException:
                  src.length=4 srcPos=0 dst.length=31 dstPos=28 length=4
```

`buildAvcC()` 分配的长度写成 `5 + 2 + sps.length + 1 + 2 + pps.length`，
但实际写进去的是 11 个固定字节（配置版本 1 + profile 3 + lengthSize 1 +
SPS 个数 1 + SPS 长度 2 + PPS 个数 1 + PPS 长度 2）。**正好少 1 个字节。**

平时看不出来，是因为 `findNal` 拿到的 SPS 长度随机型变：
只要 `sps.length + pps.length` 恰好让越界发生在「最后一个字节」上就必然崩。
华为这台给的是 17 字节 SPS + 4 字节 PPS → 分配 31、实际要 32 → 最后一字节越界。

崩了之后被 `onEncoderFormatChanged` 里的 `catch (Throwable)` 吞掉，只打一行 warning，
于是 `vcfg` 永远不发、画面永远不来，表现是「连得上，但没有画面」。
**测试全绿是因为没有任何一条测试碰过这段代码** —— `test-h264-e2e.js` 用的是
预先录好的 `desc`，验的是解码侧，而这段是编码侧。

**4. 同一个函数里 `lengthSizeMinusOne` 写错，就算不崩画面也是花的。**

按 ISO/IEC 14496-15，第 5 个字节是 `bit(6) reserved = '111111'` + `unsigned int(2) lengthSizeMinusOne`。
要 4 字节长度前缀就得是 `0xFF`；原代码写的是 `0xFC`，低两位 = 0 → 声明成 **1 字节**长度，
而 `annexBToAvcc()` 实际写的是 **4 字节**长度，解码器会按 1 字节去切，画面必花。

这条是**新加的单元测试抓出来的**，不是真机抓的 —— 第 3 条修好之后，
我给它补了 `AvcCTest`（26 项断言），第一次跑就红了一项 `lengthSizeMinusOne 低两位 = 3`。
说明「把这段从 Android Service 里挪出来、变成纯 Java 可单测」是值得的：
`buildAvcC` 原来埋在 `CaptureService` 里，不启动模拟器就没法测。

**5. 补发关键帧（针对「手机放公司」这个场景）。**

`MediaProjection` 只在屏幕变化时产帧。手机放公司停在打卡界面不动，
你从家里连上去就是一片空白。现在被控端会把最近的关键帧缓存住，
新控制端一连上（中继发 `controller-joined`，或它自己发 `codec` 请求）就补发。
同一个关键帧 1.5 秒内只补一次，避免在流量卡上白发一遍 65KB。

配套还修了这些：

- **`releasePipeline()` 里要清掉缓存的关键帧**。旋转 / 改画质 / 换编码都会重建管线，
  新编码器的 SPS 和尺寸可能都不一样，拿旧关键帧喂新解码器就是花屏。
- **日志会骗人**：`onStop()` 回调里一律打「MediaProjection 已被系统停止」，
  但 `stopEverything()` 自己也会调 `projection.stop()`，于是**我们主动收尾**也被记成
  「系统停了」。排查时被这条日志带偏过一次，现在用 `stoppingByUs` 区分，
  顺带也避免了 `stop()` → `onStop()` → `stopEverything()` 的重入。
- **轻点有个 400~600ms 的「死区」**：`touchend` 里判定轻点要求 `dur < 400`，
  而长按的定时器是 600ms 才触发。于是**按住 400~600ms 再松手，手机上什么反应都没有** ——
  两个分支都进不去。阈值已对齐成 600：`< 600` 一律算轻点，`>= 600` 时长按已经发过了
  （`moved` 被置 true，`touchend` 开头的 `if (moved) return` 会拦掉），不会重复发。
  这是端到端测试偶发失败时才顺出来的：机器一忙，CDP 往返让按住时长超过 400ms，
  测试就报「一条指令都没发」。
- **测试选点要谨慎**：端到端测试原本在画面 75% 高度处点一下，
  结果正好命中被控端 App 自己的「停止」按钮，会话被自己停掉，
  看起来特别像「触摸注入有 bug」。实际坐标映射是准的（0.75 × 2340 = 1755，
  而那一刻「停止」按钮的 y 就是 1754~1898）。现在改成点正中心，
  并且加了一条「点完之后会话还活着」的断言钉住它。

**6. `startH264()` 里有一个竞态，会让「画面能看、但怎么点都没反应」。**

这条是**第 1 条那个 bug 的孪生兄弟，藏在另一个地方**，而且是端到端测试反复偶发失败
（一会儿 20 项全过、一会儿「一条指令都没发」）才被逼出来的。

`startH264()` 里原本有这么一行：

```js
dec.configure(cfg.codec, cfg.desc, cfg.w, cfg.h).then(function (ok) {
  if (!ok) { ...; return; }
  codecMode = 'h264';
  imgW = 0; imgH = 0;        // ← 就是这里
```

`configure()` 是**异步**的。等它的 promise resolve 时，解码器很可能**已经解出第一帧**
并调过 `onSize()` 把 `imgW` 设成 720 了 —— 这一行再把它清成 0。
而解码器只在**尺寸发生变化**时才回调 `onSize()`，后面同样尺寸的帧不会再来一次，
于是 `imgW` 永远是 0：`touchstart` / `touchend` 开头的 `if (!imgW) return` 把
所有触摸静静吞掉。**画面是好的，点哪儿都没反应，而且时好时坏，纯看
`configure()` 和第一帧谁先到。**

修法就是**不要清**。屏幕尺寸是设备的属性，跟编码方式没关系；`setSize()` 本身
带了「尺寸没变就直接返回」，尺寸真变了它会自己应用，所以不清完全没副作用。

诊断过程也值得记一下：这个 bug 的表象是「测试说一条指令都没发」，
但页面上 `touchstart`/`touchend` 都正常触发了、`changedTouches` 也有值。
如果只看「事件有没有到」，会误判成坐标换算有问题。
**在 `touchend` 开头那一堆 `return` 里，`!imgW` 和 `moved` 是最容易被忽略的两个。**
最后是靠在自己的 capture 监听里量出 `dur=86ms / dist=0`（都远在阈值内）
才把嫌疑范围缩到那两个 `return` 上。

### 7. 「按文字点」会点到屏幕外的坐标（文字模式的 bug，第一次真机跑就露出来了）

第一版「读屏」功能跑通之后，dump 出来的坐标是这样的：

```
 1.    远程协助 · 被控端   @307,-701
 2.    ...三步：填服务器地址 → 开无障碍 → 点开始。   @540,-638
 4. 👆 127.0.0.1   @409,-509
```

**y 是负的。**原因是界面被滚动过 —— `getBoundsInScreen()` 返回的是**屏幕坐标系**，
滚出可视区的节点自然就是负坐标。而第一版 `tapByText()` 是这么写的：

```java
List<AccessibilityNodeInfo> exact = ...;   // 只按文字匹配，没看它在不在屏幕里
AccessibilityNodeInfo hit = !exact.isEmpty() ? exact.get(0) : ...;
tapAtPx(r.centerX(), r.centerY());          // 照着 -509 点下去
```

后果：**能匹配到文字 ≠ 能点到它。**照负坐标派发手势，会落到屏幕边缘，
点到什么全凭运气 —— 而且日志里还显示「点击成功」，非常难查。

两处都改了：

1. `collectUi()` 给每一项加了 `v` 字段（在不在屏幕里），`readUi()` 里补上屏幕尺寸
   `sw`/`sh`。控制端把屏幕外的行标灰，点它的时候自动带上 `scroll: true`。
2. `tapByText()` 改成**只点屏幕内的元素**，找不到就如实说：
   `找到了「XX」，但它在屏幕外（y=-509），没有点击`。
   带 `scroll: true` 时会先往上滚（最多 6 次，每次 60% 屏高）再找，
   仍然找不到就直接放弃，不瞎点。

另外 `tapAtPx()` 也补了坐标夹取 —— 之前它和 `toPx()` 不一样，没有 clamp，
负坐标会原样发出去。

这条的教训跟第 1 条（`buildAvcC`）是一回事：**「读到了」不等于「能操作」，
中间那层坐标系转换必须显式验证。**现在 `verify-unattended.js` 里有一条专门断言
「屏幕外的元素被拒绝点击」，就是防它再回来。

**补丁之后又冒出来第二个问题：滚动只会朝一个方向翻。**

`scrollStep()` 第一版固定从屏幕 75% 划到 15%（内容向上走），也就是**只会往下找**。
把界面滑到底之后再测，标题跑到了 y=-1347（视口**上方**），
于是 6 次滚动全在往下翻，越翻离目标越远，最后报「找不到」。

修法是**看目标在哪边决定方向**：`centerY() < 0` 说明在上方，就从 15% 划到 75%
（内容向下走）；否则反过来。测试也相应改成上下两个方向各验一次 ——
只测一个方向的话，这个 bug 会一直躲着。

---

写测试不只是「证明能跑」，下面这两条也是测试逼出来的真问题：

**1. 切换编码之后触摸会短暂失灵。**
`fallbackToJpeg()` 里原本会把 `imgW = 0` 清掉。屏幕尺寸是**设备的属性**，
不随编码方式变，清掉纯属多余。平时看不出问题，因为 JPEG 第一帧到了
`drawJpeg()` 会把尺寸补回来；但如果被控端是「只支持 JPEG、直接回绝 H.264」那种
（它不会重建管线，也就不会再发一次 `meta`），`imgW` 就永远是 0，
之后所有触摸都被 `if (!imgW) return` 静静吞掉 —— 画面能看，但怎么点都没反应。

**2. 横屏之后点不准。**
「横屏」是给 `#surface` 加 `rotate(90deg)`。但 `getBoundingClientRect()` 对旋转元素
返回的是**转之后的外接矩形**，宽高是互换的，直接按 `left/top` 相除会算错 ——
越靠边错得越多，只有正中心是对的。现在按绕中心逆时针 90° 反推回未旋转的坐标，
测试里用 CDP 派发真实触摸，验证 (0.25, 0.75) 转完还是 (0.25, 0.75)。

### 8. 界面上的输入框不回填，会把用户配好的东西静默清掉

这个是做加密连接时自己写出来的 bug，而且**测试还差点把它放过去**。

场景：App 里加了「服务器证书指纹」这一栏。设计时想着「框里是你要断言的，
下面那行小字显示当前生效的」，所以**故意不回填**已保存的指纹 —— 觉得这样语义更清楚。

后果：用户填好指纹、连上一次、一切正常。下次打开 App，框是空的，
直接点「开启文字模式」—— 按钮的 handler 里有一句

```java
if (pin == null) e.remove(AgentTls.K_TLS_PIN);   // 框空着 = 用户想清掉
```

于是**指纹被删掉了**，连接从「严格校验」静默降级成 TOFU。
界面上什么都没变，用户完全看不出来。

**是怎么发现的**：验证「指纹配错会不会被拒绝」时，我用 `run-as` 直接往
SharedPreferences 里写了一个错误的指纹，结果手机上**照样连上了**，
日志里还老老实实写着「首次连接（TOFU）」。

第一反应是「TLS 校验没生效」—— 这个结论是错的。真实原因是：
写进去的指纹被界面按钮那句 `remove` 抹掉了，服务读到的就是「没有指纹」。

**教训有两条**：

1. 凡是「读出来显示 + 再写回去」的配置项，**界面必须回填**。
   不回填的话，「空」既表示「用户想清空」也表示「我没显示出来」，两种含义混在一起，
   必然出事。修法就是老老实实回填，让「空」只剩一个含义。
2. 用 `run-as` 改 prefs 做测试时，**要确认没有别的代码路径会重新保存 prefs**。
   否则你以为在测 A，其实测的是「配置被抹掉之后的默认行为」——
   现象和真 bug 一模一样，但方向完全错了。

修完之后界面上那行小字也改了措辞：不再说「指纹来源：手动填写 / 已记住」，
而是直接说「将严格校验这个指纹」，因为框里就是唯一的事实来源。

## 十、手机放公司、人在家里用 iPhone 控制打卡 —— 怎么部署

这是最实际的一种用法，但它和「局域网里两台设备互相连」完全不是一回事，
有两处必须换做法，先说清楚再动手。

### 10.1 必须换掉的一点：家里连不到公司的内网

现在的 `server.js` 是**局域网中继**：它要求控制端能直接访问到跑 `server.js` 的那台电脑。
如果服务器在公司内网（比如 `10.253.120.x`），你家 iPhone 是**访问不到**它的。

顺带说明几个常见误区：

| 想法 | 为什么不行 |
|---|---|
| 「两个手机都有电话卡，用流量直连」 | 两边通常都在运营商 NAT（CGNAT）后面，互相看不到对方，也没法打洞 |
| 「iPhone 开热点给安卓连」 | 热点网段是 `172.20.10.0/28`，不是公网地址，家里这边照样访问不到 |
| 「安卓开热点让 iPhone 连」 | 安卓开热点时通常会把 WiFi 关掉；而且热点一旦关了连接就断了 |
| 「把公司电脑的端口映射出去」 | 公司网络一般不允许，也没有公网 IP |

**能走通的路子只有一条：中继服务器放在一个双方都能访问的地方。**

两种做法：

**A. 买台最便宜的云服务器（推荐）**

把 `server.js` 丢到 VPS 上跑起来，然后：

- 公司那台安卓手机：**用自己的流量卡**（或公司 WiFi）连到 `VPS_IP:8081`
- 家里的 iPhone：连到 `https://VPS_IP:8080`

两边都是「主动往外连」，所以 VPS 不需要任何入站端口放行以外的特殊配置，
公司内网也不用动。这是最省心的方案，一台 1 核 1G 的最低配就够 ——
中继只做转发、不解码不落盘。

> 项目里已经准备好了 `deploy/` 目录，包含：
> - `docker-compose.yml`（relay + Caddy）
> - `Caddyfile.letsencrypt`（有域名，自动 HTTPS）
> - `Caddyfile.selfsigned`（无域名，自签证书）
> - `self-signed.sh`（在 VPS 上生成证书 + 打印指纹）
> - `.env.example`（所有环境变量）
>
> 完整部署说明见 `deploy/README.md`，最快三步：`cp .env.example .env` →
> `cp Caddyfile.letsencrypt Caddyfile` → `docker compose up -d`。
>
> 不想用 Docker 的话，README 11.8 也有裸机 systemd 配置。

> **⚠ 上公网之前先做加密。** 现在默认是明文：配对码、屏幕画面、你在控制端敲的
> 密码都在线上裸着，同一条链路上任何人都能读到甚至改掉。
> 加证书只要三步，见**第十一节**。这不是「有空再优化」，是前置条件。
>
> **⚠ 同时要设 `HEALTH_TOKEN`。** 不设的话 `https://VPS_IP:8080/health` 会把
> 当前在线的配对码直接公开出来 —— 那就不用猜了。另外建议在 VPS 防火墙上
> 只放行你家和公司的出口 IP 访问 8081。详见 **11.9**。

**B. 不买服务器，用隧道把公司电脑暴露出去**

在跑 `server.js` 的那台公司电脑上装个隧道（Cloudflare Tunnel / frp / ngrok），
把 8080 暴露成一个公网域名，家里的 iPhone 访问那个域名。
**但这条路有个前提**：公司那台安卓手机必须和公司电脑在**同一个局域网**里
（也就是手机要连公司 WiFi）。如果手机只用自己的流量卡，它就连不到公司电脑，
这条路直接不成立。

> 你现在的测试环境就卡在这里：公司电脑只有有线网卡（`以太网 2`，`10.253.120.21`），
> `netsh wlan show interfaces` 显示**系统上没有无线接口**，所以它没法加入
> iPhone 热点，手机也没法和它互通（实测 ping 100% 丢包）。
> 所以本机测试只能靠 USB 隧道（见 10.4），真部署请选 A 或 B。

### 10.2 「不想 iPhone 连的时候还要同意」—— 分两件事

**iPhone 这一侧：本来就不需要同意。**

用 Safari 打开 `http://你的地址:8080`，填配对码就能连，没有任何确认弹窗。
两点注意：

- **别用内网 IP 访问**。iOS 14+ 在网页访问局域网地址时会弹
  「此网站想要查找并连接本地网络中的设备」，要你点允许。用公网域名 / 公网 IP 就没这一下。
- 想更像一个 App：Safari 里「添加到主屏幕」。但**加了之后震动就没了** ——
  震动靠的是 Safari 里 `<input type=checkbox switch>` 的默认行为，
  独立运行的网页 App 拿不到。要震动就别加到主屏幕。

**安卓这一侧：`MediaProjection` 的授权弹窗是系统强制的，绕不过。**

这是 Android 的安全设计，不是本程序偷懒。但要注意它的**实际约束没那么紧**：

- **只需要点一次**，不是每次连接都要点。授权跟着「录屏会话」走，
  只要被控端 App 的采集服务一直活着，后面无论连多少次都不用再点。
- 所以正确用法是：**在公司把手机架好、点一次「开始接受远程协助」、点一次「允许」，
  然后让服务一直跑着**，之后再从家里连就不用管了。
- 会打断它的只有三种情况：**手机重启**、**系统回收了这个服务**、
  **别的应用开始录屏**（Android 同一时刻只允许一个录屏会话）。
  这三种都得有人到现场再点一次。

**如果「现场没人」是硬要求**，那就别走「看画面」这条路 ——
改成只用无障碍服务「盲操作」：让被控端读界面文字、按文字点，不看画面。
这条路**完全不需要录屏授权**，也就没有弹窗。
**这套已经做好了**，见第十二节。

### 10.3 关于「打卡」这个具体场景的提醒

- **通知会一起被看到。** 录屏是整个屏幕，锁屏通知、微信弹窗都会出现在画面里
  （实测时就看到了「顺丰快递已揽件」这类通知）。介意的话把通知在锁屏上隐藏。
- **打卡 App 可能有反自动化检测。** 部分考勤 App 会检查无障碍服务、
  虚拟定位、root、模拟器。无障碍点击在它看来是「无障碍用户操作」，
  有的会拒绝。先用几次观察一下，别把它当成 100% 可靠。
- **别让屏幕锁上。** 锁屏后录屏拿到的就是锁屏界面，而且无障碍在安全锁屏上点不了。
  在开发者选项里开「充电时不锁定屏幕」，或者把息屏时间调长。
- **插着电。** 长时间录屏很费电，而且华为等厂商对「长时间前台服务」有额外的回收策略。

### 10.4 在本机（Windows + USB）上测试时怎么接

如果只是想先把链路跑通，不折腾公网，用 USB 隧道最快：

```bash
# 1) 让 adb 服务常驻，否则每次命令结束它可能被回收，reverse 隧道会一起没掉
adb -a -P 5037 server nodaemon     # 放后台跑

# 2) 建立反向隧道：手机上的 127.0.0.1:8080/8081 -> 电脑的 8080/8081
adb reverse tcp:8080 tcp:8080
adb reverse tcp:8081 tcp:8081

# 3) 被控端 App 里「服务器地址」填 127.0.0.1，端口 8081
```

然后电脑上 `node server.js`，手机连 `127.0.0.1:8081` 即可。

**为什么要把 adb 服务放后台常驻**：adb 服务进程被回收时，`adb reverse` 建立的隧道
会**一起消失**，手机就连不上服务器了，而且现象是「刚才还好好的，突然就连不上了」，
很难查。用 `server nodaemon` 常驻可以避免。

**华为手机装 APK 会被 AppGallery 拦截。** `adb install` 会弹出「风险提示」
然后被转交 AppGallery 的「安全提醒」页面，页面上有一个**未勾选的复选框**
（「已了解此应用未经检测，可能存在风险…」）。**不勾选这个复选框，「继续安装」
按钮是灰色的、disabled 状态** —— 这就是之前我误以为「Activity 完全不吃输入」
的真正原因：我一直在点一个 disabled 按钮，还以为是界面无响应。

所以绕过 AppGallery 是最干净的办法：临时停用，装完再恢复。

```bash
# 1. 屏幕要亮着，否则弹窗画不出来
adb shell svc power stayon true

# 2. 应用不能还在跑，否则 InstallStaging 会卡
adb shell am force-stop com.wb.remoteagent

# 3. 临时停用华为应用市场（风险检查就在它里面）
adb shell pm disable-user --user 0 com.huawei.appmarket

# 4. 安装
adb install -r --no-streaming dist/remote-assist-agent.apk

# 5. 恢复应用市场
adb shell pm enable --user 0 com.huawei.appmarket
```

用 `--no-streaming` 是为了避免华为 ROM 的 streaming 相关 staging 问题。
AppGallery 停掉后，安装走 AOSP 的 PackageInstaller，只有一个「风险提示」
弹窗，点一次「继续安装」就过了。

如果上面这条路因为系统限制走不通，还有一个备选：**会话式安装**
（全程不碰任何 UI）：

```bash
bash tools/install-apk.sh
```

它内部做的是 `install-create` → `install-write` → `install-commit`。
几个坑写在脚本注释里了，这里也记一下：

- `install-write` 必须传**文件路径**，传 `-`（走 stdin）经 `adb shell` 会被截断，
  报 `failed to write; Unexpected EOF`。
- 安装前**屏幕必须是亮的**，否则 `InstallStaging` 画不出来，一样卡死。
- **待更新的那个应用自己不能还在跑。** 实测：应用的后台 Service 还活着时，
  `install-commit` 会一直卡在 `InstallStaging`（**即使屏幕是亮的、还开了 stayon**）。
  同一条脚本，先 `am force-stop` 掉应用再跑就顺利装完了。
- 卡住之后恢复办法：`pm install-abandon <会话号>` + force-stop
  `com.huawei.appmarket` 和 `com.android.packageinstaller`。
- 手机上**必须真的有网**（人机验证要联网），否则会在「安全提醒 ↔ 人机验证」之间
  死循环，详见 12.6。


### 10.5 真机验证脚本

```bash
# 看被控端到底有没有在推画面（不需要浏览器，只统计字节流）
node server/probe.js JC484UQK 10

# 端到端：真的开一个无头 Chrome，打开控制端页面连上真机，
# 验证画面真的被解码并画到了 canvas 上，触摸坐标也准
node server/verify-real-device.js JC484UQK

# 文字模式（无人值守）：读屏 / 按文字点 / 屏幕外拒绝点击 / 没有视频流
node server/verify-unattended.js JC484UQK
```

`probe.js` 会明确告诉你「屏幕静止时补发的那个关键帧」是正常的，
不会因为只有 1 帧就报 0 fps 让你以为卡死了。

## 十一、加密（TLS / WSS）—— 放到公网之前必须做

### 11.1 为什么非做不可

不加证书时，中继的两个口都是明文：

- **8080 控制端**：`ws://`，配对码、界面文字、你在控制端敲的密码，全在线上裸着
- **8081 被控端**：裸 TCP，配对码 + 屏幕画面（录屏模式下是 JPEG / H.264 流）明文传输

局域网里凑合能用。**一旦放到公网，等于把这些东西贴在网上** ——
同一个 WiFi 下、同一个运营商出口下，或者链路上任何一跳，都能直接读到，
甚至改（比如把「点击坐标」改掉）。

而第十节说的部署方案恰恰就是「放到公网 VPS」。所以加密不是可选项，是前置条件。

### 11.2 三步开起来

```bash
# 1. 生成证书（顺手打印指纹）
bash tools/make-cert.sh

# 2. 带证书启动
TLS_CERT=server/certs/cert.pem \
TLS_KEY=server/certs/key.pem \
node server/server.js

# 3. 手机 App：勾上「加密连接（TLS）」
```

**控制端（iPhone）不用做任何改动**。页面是按 `location.protocol` 自己选 `ws://` 还是
`wss://` 的，走 https 打开就自动是 wss。

同一个证书同时用在两个口上：控制端变成 `https` + `wss`，被控端的裸 TCP 外面套一层 TLS。
被控端 App 里要勾「加密连接」——**不勾就连不上**，这是故意的，不是 bug。

### 11.3 指纹那一栏怎么填

两种都支持：

| 做法 | 安全性 | 什么时候用 |
|---|---|---|
| **填指纹** | 从第一次连接起就是严格校验 | 推荐。指纹从 `make-cert.sh` 的输出里复制 |
| **留空（TOFU）** | 第一次连接记下指纹，之后每次严格比对 | 懒得填。方便，但第一次连接挡不住主动中间人 |

TOFU（Trust On First Use）的代价是固有的：第一次连接时客户端还没有任何参照物，
真有个中间人在场也发现不了。所以界面上会把**当前生效的指纹显示出来**，
你可以和服务器上 `make-cert.sh` 打印的核对一下 —— 对得上就说明没被顶替。
核对完就等于把 TOFU 补成了严格校验（因为指纹已经记住了）。

指纹格式随便：带冒号、不带冒号、小写、中间有空格，都能识别。

### 11.4 自签证书 vs 正式证书

| | 自签（`make-cert.sh`） | Let's Encrypt |
|---|---|---|
| 成本 | 5 秒钟 | 要一个域名，certbot 续期 |
| 浏览器 | Safari 会警告「此连接非私人连接」，点「继续访问」即可 | 没有警告 |
| App | 要处理指纹（填或 TOFU） | 系统信任库直接认，指纹可以不填 |
| 适用 | 自己用、能接受点一下警告 | 想干净、或者要分享给别人用 |

`make-cert.sh` 会自动把本机所有局域网 IP 写进 SAN —— 这一步别省，
现在浏览器和安卓都**只看 SAN 不看 CN**，少写一个 IP，用那个 IP 访问就报「证书不匹配」。

### 11.5 挂在 nginx / caddy 后面

中继自己就能终结 TLS，多数情况下不需要反代。但如果你已经有反代（想复用 443、
想加 basic auth、想上 CDN），可以这样：

```nginx
location / {
    proxy_pass http://127.0.0.1:8080;
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;      # WebSocket 必须
    proxy_set_header Connection "upgrade";
    proxy_set_header X-Forwarded-For $remote_addr;
    proxy_set_header X-Forwarded-Proto $scheme;
}
```

这时中继那边：`TRUST_PROXY=1`，并且**不要再设 `TLS_CERT`**（TLS 已经由反代终结了）。

`TRUST_PROXY` 默认是关的，这点很重要：开着的话，任何客户端都能自己编一个
`X-Forwarded-For` 来污染日志。只有确实在反代后面才打开。

### 11.6 环境变量速查

| 变量 | 作用 | 默认 |
|---|---|---|
| `TLS_CERT` / `TLS_KEY` | 控制端 https/wss 的证书 | 不设 = 明文 |
| `TLS_TCP_CERT` / `TLS_TCP_KEY` | 被控端单独用另一张证书 | 复用 `TLS_CERT`/`TLS_KEY` |
| `TLS_AGENT=0` | 只给控制端加密，被控端仍走裸 TCP | 关（有证书就两边都加密） |
| `TRUST_PROXY=1` | 信 `X-Forwarded-For` / `-Proto` | 关 |
| `HEALTH_TOKEN=<随机串>` | 不带令牌就看不到 `/health` 里的配对码 | 不设 = 公开（会警告） |
| `RATE_LIMIT_DISTINCT` | 窗口内允许试几个**不同**的错配对码 | `6` |
| `RATE_LIMIT_TRIES` | 窗口内允许的总尝试次数 | `80` |
| `RATE_LIMIT_WINDOW_MS` | 统计窗口 | `300000`（5 分钟） |
| `RATE_LIMIT_BLOCK_MS` | 触发后封多久 | `600000`（10 分钟） |
| `RATE_LIMIT=0` | 关掉猜码限流（只在可信内网用） | 开 |
| `HTTP_PORT` / `TCP_PORT` | 端口 | `8080` / `8081` |

启动日志会明确告诉你每条链路加没加密，没加密还会打一个醒目的警告框；
`/health` 没设令牌、或者限流被关掉时，也会各打一条警告。

### 11.7 怎么确认加密真的在生效（而不是「配了就算」）

这是最容易自欺欺人的地方。**证书配了、客户端把校验关掉了**，这种情况下
所有正常路径的用例都是绿的，但中间人照样能解密 —— 加密成了心理安慰。

所以 `server/test-tls.js` 里有三条**反向断言**，专门验「连不上」：

| 断言 | 证明什么 |
|---|---|
| 用一张无关 CA 连 `wss` → 必须失败 | 服务器确实在出示自己的证书，且客户端确实在校验链 |
| 用一张无关 CA 连被控端 TLS 口 → 必须失败 | 被控端口真的是 TLS，不是「配了证书但还在跑明文」 |
| 不给 CA、走系统信任库 → 必须失败 | 自签证书没被谁偷偷塞进信任库 |

再加上「明文连 TLS 端口必须拿不到任何数据」和「二进制画面逐字节一致」，
一共 29 条断言。实测全绿。

顺带一个设计说明：App 端**没有**用 `rejectUnauthorized=false`（信任所有证书）那种写法。
那样加密还在，但任何人都能拿一张自签证书冒充服务器，等于没加密。
`AgentTls` 里只有两条通过路径：指纹命中，或者系统信任库认可。

### 11.8 部署到 VPS（systemd）

```ini
# /etc/systemd/system/remote-assist.service
[Unit]
Description=remote-assist relay
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=relay
WorkingDirectory=/opt/remote-assist
Environment=HTTP_PORT=8080
Environment=TCP_PORT=8081
Environment=TLS_CERT=/etc/ssl/relay/cert.pem
Environment=TLS_KEY=/etc/ssl/relay/key.pem
# 公网必须设：不设的话 /health 会把在线配对码公开出去
Environment=HEALTH_TOKEN=换成一段随机串
# 挂了反代就必须设，否则按 IP 的限流会把所有客户端当成同一个人
Environment=TRUST_PROXY=1
ExecStart=/usr/bin/node server/server.js
Restart=always
RestartSec=3
NoNewPrivileges=true
PrivateTmp=true

[Install]
WantedBy=multi-user.target
```

```bash
sudo systemctl enable --now remote-assist
sudo journalctl -u remote-assist -f      # 看启动日志里那几行加密状态
```

防火墙只需要放行 8080（控制端）和 8081（被控端）。两边都是主动外连，
所以**不需要**任何入站端口转发、也不需要在公司内网开洞。

### 11.9 猜配对码的防护（已做）和它挡不住什么

TLS 解决的是「传输过程不被偷看篡改」，它**不解决**「配对码被猜出来」。
这一节说清楚两个真实的攻击面，以及现在是怎么挡的。

#### 两个攻击面

**（1）控制端口是猜码的廉价探测器。**
控制端 `hello` 一个不存在的码时，服务器会顺手把房间建出来（这是为了兼容
「先开控制端、后被控端才上线」这个顺序）。所以一次猜测的成本只是
「一条 WebSocket 连接 + 一个小 JSON」。而 `welcome` 里那个 `agent: true/false`
就是现成的答案 —— 猜中了会变成 `true`。

**（2）被控端口更糟：猜中一个在线码 = 把真被控端顶下线。**
被控端连上来时会顶掉同一房间里原来在线的被控端（这是治僵尸连接的必要机制：
手机换网时旧 socket 可能半死不活，不顶掉就永远连不回来）。
所以猜中一个码不只是「看一眼」，而是**接管控制端发来的按键**。

#### 现在怎么挡：按「试过几个**不同**的码」封 IP

默认参数：**5 分钟内试满 6 个不同的错配对码，就封这个 IP 10 分钟**。
被拒时回一条 `error`（带 `retryAfterMs`），然后断开。

判「失败」的口径两端不同，因为两端的「成功」定义不同：

| 入口 | 什么算失败 |
|---|---|
| 控制端 | 连进去发现房间里没有在线被控端 |
| 被控端 | 连上去把原来在线的被控端顶掉了 |

闸门卡的是**不同码的个数**，不是总次数。这是这一节最要紧的设计决定：

> 正常用户的行为是「拿**同一个**码反复重试」（被控端还没上线、打错了又改回来），
> 攻击者必须试**很多个不同的**码。按次数封会把正常用户一起封掉，按不同码封不会。

`server/test-ratelimit.js` 专门验了这条：**同一个码连 12 次全部放行**，
换成不同的码第 4 个就被拒。一共 36 条断言，全绿。

几条容易写错的细节，都在测试里钉住了：

- **记账发生在 join 成功之后**，所以「试满第 N 个不同码」那一次本身是放行的，
  从第 N+1 次请求才开始拒。`DISTINCT=6` 的实际效果是「每个封禁窗口里
  最多白拿 6 个码的答案」。
- **封禁是按 IP 的，不是按码的** —— 封禁期间连**对的**码也进不去。
  否则攻击者只要在试错的同时混着试真码就能绕过。
- **成功一次就把这个 IP 的账清掉**，正常用户不会被历史失败拖着。
- **封禁期间猜码的人顶不掉在线被控端了** —— 测试里专门造了一个在线房间，
  确认封禁期内顶替被拒、解封后原被控端还活着。
- 控制端页面收到 `retryAfterMs` 后会把重连推迟到解封之后。
  不这么做的话它会 800ms 一次地一直撞墙（WebSocket 握手本身是成功的，
  所以 `onopen` 每次都把指数退避清零，退避形同虚设）。

#### `/health` 会泄露在线配对码（这个比猜码严重）

默认 `/health` 是公开的，而 `rooms[].code` **就是**当前在线被控端的配对码。
公网上等于把答案直接贴出来，再好的限流也没意义。所以加了令牌：

```bash
HEALTH_TOKEN=<一段随机串> node server/server.js
```

设了之后不带 `?token=` 就拿不到 `rooms`（其它字段照常返回，nginx 健康检查不受影响）。
没设的话启动日志会打一个警告框。

#### 挡不住什么（说清楚）

1. **猜中一次就完了。** 限流压的是**枚举**，不是「一次幸运命中」。
   真正的底线还是配对码的空间：32⁸ ≈ 1.1×10¹²。
   限流把「用僵尸网络几小时内磨出来」变成「不现实」，但没把概率变成 0。
2. **`TRUST_PROXY` 配错的后果是灾难性的。**
   挂了反代却没开 `TRUST_PROXY=1`，所有客户端在服务器眼里都是 `127.0.0.1`，
   一个人触发封禁会把**所有人**一起封掉（包括你自己的 iPhone）。
   反过来，**没挂反代却开了** `TRUST_PROXY=1`，攻击者每猜一个码伪造一个
   `X-Forwarded-For` 就绕过了 —— 所以这个开关默认是关的，
   测试里有一条反向断言专门钉「默认配置下伪造 XFF 绕不过」。
3. **被控端那条链路在反代下没法按真实 IP 记账。**
   它走裸 TCP/TLS，没有 HTTP 头可取，反代下只能看到反代自己的 IP。
   这一层应用层解决不了 —— 公网部署请**给被控端端口做 IP 白名单**
   （只允许公司的出口 IP 连 8081）。这是目前最有效的单条措施。
4. **被控端和控制端共用同一个 IP 额度。** 同一个 IP 上两个口子互相影响。
   正常用法（手机和浏览器在不同网络）不受影响。

#### 公网部署的推荐组合

| 层 | 做什么 |
|---|---|
| 反代 IP 白名单 | **8081 只放公司的出口 IP**，8080 放你家 + 公司（最有效） |
| `HEALTH_TOKEN` | 设上，别把在线配对码贴出来 |
| `TRUST_PROXY=1` | 挂了反代就**必须**开，否则限流会把所有人一起封 |
| basic auth（可选） | 8080 上再加一道口令 |
| 换配对码 | App 里点一下就行，定期换 |

前四条都是配置，不用改代码。

## 十二、无人值守模式（不录屏）—— 「手机放公司没人点授权」的正解

### 12.1 为什么非得另做一个模式

第十节说了，`MediaProjection` 的授权弹窗是系统强制的，**绕不过**。它只需要点一次，
但「一次」也要有人在现场 —— 而手机重启、系统回收服务、别的应用开始录屏，
这三种情况都会把那次授权弄丢（实测时手机上装了 AirDroid，它一录屏就会把我们踢掉）。
手机放在公司、人已经回家，这三件事一旦发生就彻底失联。

**但「打卡」这个需求其实不需要看见画面。**知道现在停在哪个界面、按钮上写的是
「上班打卡」四个字，就够了。而无障碍服务能把这些读出来 —— 它**完全不需要录屏授权**。

所以加了第二种模式：同一个 App，界面上「4. 无人值守」那一块，
点「开启文字模式 · 待命」即可。

| | 录屏模式 | 文字模式 |
|---|---|---|
| 启动时的授权弹窗 | 有，系统强制 | **没有** |
| 控制端能看到 | 画面 | 只有界面文字 |
| 能开机自启 | 不能（弹窗点不了） | **能**（但要过厂商白名单，见 12.3） |
| 流量 | 几百 kbps ~ 几 Mbps | 可以忽略 |
| 代码 | `CaptureService` | `UnattendedService` |

中继会用 `hello` 里的 `mode` 字段把这个信息转给控制端
（`welcome` / `agent-online` / `/health` 里都能看到），
控制端据此切换界面：不再等视频，工具栏多出「读屏」，画面区显示一句说明。
**没声明 `mode` 的老被控端一律按 `video` 处理**，所以这个改动是向后兼容的。

### 12.2 怎么用

被控端（公司的安卓手机）：

1. 填服务器地址和配对码（和录屏模式共用同一份配置）。
2. 开无障碍服务（**文字模式全靠它，没它这个模式没有任何意义**）。
3. 点「开启文字模式 · 待命」。**没有任何弹窗**，通知栏出现一条常驻通知。
4. 想让它重启后自己回来，把「开机自动启动」打开，并做 12.3 那一步。

控制端（家里的 iPhone）：照常打开控制端页面、输配对码。
连上之后会直接跳到「读屏」面板，列出当前界面上的所有文字，
可点的那几行前面有个 👆，点一下 = 让公司那台手机点那个控件。
点完 700ms 会自动再读一次，把点完的结果送回来。

命令行下也能直接调：

```js
{ t: 'dump' }                              // 读屏
{ t: 'taptext', q: '上班打卡' }             // 按文字点（只点屏幕内的）
{ t: 'taptext', q: '上班打卡', scroll: true }  // 找不到就往上滚几屏再找
{ t: 'open', label: '钉钉' }                // 按应用名打开（不用记包名）
{ t: 'apps' }                              // 列出可启动的应用
{ t: 'ping' }                              // 探活
```

每条指令都会回一条 `{t:'ack', op, ok, msg}`，`msg` 是能直接给人看的中文说明。

### 12.3 开机自启在国产 ROM 上要额外放行一次（实测）

**这一条是实测踩出来的，不是推测。**

在华为 P30 Pro（EMUI 10 / Android 10）上，代码是这样的：
接收器在 manifest 里注册得好好的（`dumpsys package` 里能看到三个 action 都在），
包状态也正常（`stopped=false notLaunched=false`），
但重启之后**服务就是不回来**。查 logcat 只有：

```
BroadcastQueue: Finished with ordered broadcast BroadcastRecord{... BOOT_COMPLETED}
```

**广播被系统「处理完了」，而我们的 `onReceive` 一次都没被调用** —— 没有崩溃、
没有异常、没有任何关于 `com.wb.remoteagent` 的记录，就是被 EMUI 吞了。

对照实验（同一个接收器，手动发一条非保护的广播）：

| 状态 | `onReceive` 被调用 |
|---|---|
| 重启后，应用没被打开过 | **否** |
| 打开过一次应用（哪怕随后按 Home 退到后台） | **是**，服务立刻起来 |

也就是说 EMUI 的策略是：**应用不在「应用启动管理」的白名单里，就不给后台启动**，
直到用户手动打开过它。`pm install` 装出来的侧载应用默认就在名单外。

**所以要做的是一次性设置**（在公司架手机的时候顺手做掉）：

> 设置 → 应用 → 应用启动管理 → 找到「远程协助」→ 关掉「自动管理」→
> 打开「允许自启动」和「允许后台活动」

App 里加了个「打开系统的『启动管理』设置」按钮帮你跳过去。
不过华为的这个页面要求一个厂商私有权限（`com.huawei.permission.external_app_settings.USE_COMPONENT`），
第三方应用**打不开**，所以按钮在华为上会退到「应用信息」页，需要自己再点两层。
界面下方还有一行「上次开机自启：成功/失败（时间）」，用来远程确认到底有没有生效 ——
手机放公司的时候，这是唯一能判断「它到底起没起来」的线索。

### 12.4 看门狗：不用重启也能自己回来

`START_STICKY` 只在「进程因为内存压力被杀」时才会重启服务。国产 ROM 的清理策略
是把应用整个冻结或强制停止 —— 系统认为是你自己停的，不会帮你重启。

所以加了个 `WatchdogReceiver`：每 15 分钟一次的闹钟，服务不在了就拉起来。
用 `ELAPSED_REALTIME_WAKEUP` + `setInexactRepeating`，不需要精确闹钟权限
（Android 12+ 默认不给），服务本来就在前台跑着，被 Doze 推迟几分钟没影响。
用户主动点「停止」时会取消闹钟，否则刚停 15 分钟又被自己拉起来。

**能补上什么**：只要服务曾经起来过一次（用户手动打开过，或已加入自启白名单），
之后哪怕进程被杀，闹钟到点也会把它拉回来。
**补不上什么**：重启之后的那第一次，仍然要靠 12.3 的白名单。

### 12.5 这个模式的代价（说清楚，别踩坑）

- **看不到画面，只能盲操作。**控制端拿到的是「文字 + 坐标」，
  不知道界面上长什么样。第一次用建议先在能看见画面的情况下把打卡流程走一遍，
  记住按钮叫什么名字。
- **灭屏时读不到界面。**灭屏时系统没有「活动窗口」，`getRootInActiveWindow()` 返回 null。
  收到 `dump` 时会先尝试唤醒屏幕（`SCREEN_BRIGHT_WAKE_LOCK` + `ACQUIRE_CAUSES_WAKEUP`，
  这个 flag 早已废弃但仍是应用主动亮屏的唯一手段），等 1.2 秒再读。
  手机插着电放公司的话，建议把「屏幕常亮」也打开。
- **锁屏界面读不到也点不了。**手机上别设锁屏密码，或把自动锁屏时间调到最长。
- **屏幕外的元素不会瞎点。**找不到可见的匹配时会如实回一句
  `找到了「XX」，但它在屏幕外（y=-509），没有点击`，
  要滚动过去得显式带 `scroll: true`（控制端点灰色的行时会自动带上）。
- **带 `scroll` 也只能找「还在无障碍树里、只是滚出视口」的元素。**
  如果目标压根不在树里（列表用了 `RecyclerView` 那种会回收子视图的控件，
  滚远之后节点被回收了），被控端**不会**盲目来回滚 —— 它会直接回「当前界面上找不到」。
  这是故意的：瞎滚一个你不知道内容的界面，比说「找不到」危险得多。
  这条边界是实测撞出来的：`verify-unattended.js` 的 [2.6] 一度随机报红，
  查下来是**测试自己**的问题（上下两个靶子都从滚动前的那次 dump 里挑，
  测「上方」时用的已经是过期坐标），不是被控端不会滚。
- **无障碍注入在部分考勤 App 眼里是可疑的。**先用几次观察，别当成 100% 可靠。
- **文字模式下没有文件传输和取文件。**那两块要读盘/推大文件，只在录屏模式里有。

### 12.6 两个运维层面的坑（都是实测撞出来的）

**一、手机必须真的有网，否则华为连 APK 都不让你装。**

在华为上装自签 APK 要过三道关（风险提示 → AppGallery 安全提醒 → 人机验证），
第三道人机验证**要联网**。这台测试机当时 `mobile_data=0`、WiFi 也没连上
（`dumpsys connectivity` 里 `Active default network: none`），
表现是：点「继续安装」→ 弹出 `CaptchaActivity` → 立刻自己销毁 → 回到「安全提醒」，
**反复点反复循环，一句错都不报**；再点几次，系统干脆跳去「设置网络」的 WiFi 对话框 ——
这才露了马脚。

`adb shell svc data enable` 打开移动数据（有 SIM 卡就行），
`Active default network` 变成 LTE 之后，同样点两下就装上了。

**顺带一提：`pm install-create -i com.huawei.appmarket` 伪造安装来源并不能绕过第一道
「风险提示」** —— 那道关是冲着「APK 不是从应用市场来的」本身去的，跟 installer 包名无关。
试过了，没用。

**二、重新安装 APK 会把无障碍授权撤掉。**

实测：覆盖安装之后 `settings get secure enabled_accessibility_services` 里
**我们的服务被移除了**（只剩 AirDroid 那个），`dumpsys accessibility` 里
`Bound services` 也没有我们。结果就是文字模式的服务连上了、`dump` 也能回消息，
但每条指令都回「无障碍服务没在运行，读不到也点不了」—— 因为
`RemoteAccessibilityService.get()` 是 null。

**所以每次更新 APK 之后，都要到「设置 → 无障碍」里重新开一次。**
用命令行恢复：

```bash
adb shell settings put secure enabled_accessibility_services \
  "com.wb.remotesupportaddon/com.wb.remotesupportaddon.SmartService:com.wb.remoteagent/com.wb.remoteagent.RemoteAccessibilityService"
adb shell settings put secure accessibility_enabled 1
adb shell dumpsys accessibility | grep -A3 "Bound services"   # 确认真的绑上了
```

注意 `enabled_accessibility_services` 是**冒号分隔的完整列表**，
写的时候要把原有的服务一起带上，别只写自己那一个，否则会把别人的覆盖掉。
